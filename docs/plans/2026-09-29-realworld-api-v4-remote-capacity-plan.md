# Real-world API V4: two-host Linode capacity plan

**Date:** 2026-09-29  
**Status:** Approved direction; implementation in progress. No live Linode resources have been created.

## Question and scope

Measure the SLO-qualified capacity of the V3 authenticated project-management workload when the self-hosted BaaS and load generator run on **separate Linode instances in the same region**. This removes the M1 MacBook Air's shared CPU/RAM and local Docker virtualization from the measured path. It measures a specified two-host, near-client self-hosted deployment, **not** production capacity for arbitrary regions, internet users, managed BaaS offerings, or the absolute performance of a platform independent of hardware.

Create a distinct `realworld-api-v4` set only after the pilot establishes a viable topology. Preserve V3 definitions and evidence unchanged. Retain V3's fixture, workflows, access paths, stage search, SLOs, timeouts, correctness, and metric meanings initially; any necessary change to these is documented as a V4 methodological difference before collecting comparative evidence. Never pool V3 and V4 observations in one ranking or trend line.

## Proposed topology and control boundaries

```text
Mac/controller (Linode API token; orchestration; local evidence)
     | SSH administrative access, not on the measured request path
     +-- backend VM: Linux Docker Engine + Compose v2, one selected full BaaS stack,
     |               persistent fixture during a run, backend telemetry collector
     +-- runner VM: Linux + Node.js 22, pinned SDKs, V3-derived workload,
                     runner telemetry and trial output
            | private, same-region VPC connection (measured SDK/API calls)
            +----------------------------------------------> backend VM
```

The token stays **only on the controller**, in a local restricted credential store or environment variable; never put it in the repository, VM images, cloud-init, process arguments, logs, or result bundles. Live provisioning is limited to the user's approved aggregate USD $30 campaign budget. Prefer the narrowest API permissions that support instance/network creation, inspection, and deletion; if Linode requires broader permissions, document and explicitly approve that scope. SSH uses ephemeral keys or a dedicated restricted key. Neither the Docker socket nor administrative ports nor the BaaS APIs should be publicly exposed; allow only required controller management and runner-to-backend traffic. Measured runner-to-BaaS traffic uses platform-native HTTPS over the private VPC, with a per-observation private CA trusted by the runner. Do not add a shared TLS proxy to the measured path; if a platform cannot expose HTTPS natively, block that case until its platform-specific TLS solution is reviewed and documented.

Use one **fresh** backend and runner VM pair per independent observation (one complete capacity run with all stages), in a fixed region and VPC/subnet. Delete both VMs and run-owned billable resources after results are verified locally. Do not provision a new pair per load stage. **Not** a single BaaS container: Supabase, Appwrite, Nhost, Neon, etc. require their full prepared Compose topology. One backend at a time; no unrelated benchmark stacks or workloads. The baseline backend plan is the same exact 8 GiB dedicated-CPU Linode plan for every BaaS. Start the runner pilot on a separate 8 GiB dedicated-CPU plan; qualify a smaller 4 GiB runner only if it demonstrates the declared headroom. Prefer `us-west`, falling back to `us-lax`; if their current plan prices differ, choose the lower-cost region. Prefer one Linux architecture and pinned image/OS, Docker/Compose, Node/npm, source revision and `versions.env` across all runs. Do not assume local arm64 images and overrides behave identically on the selected Linode architecture: validate builds and image digests first.

### Hardware profiles and runner sizing

V4 accepts a **declared backend Linode plan ID per campaign/profile**, so separate campaigns can target, for example, 4 GiB, 8 GiB and 16 GiB backends. All platforms within a profile get the **same entire VM plan** (vCPU type/count, RAM, bundled disk/network), storage policy, region and deployment settings; RAM alone is not the variable when changing Linode plans. Record the exact plan, not just `4gb`. Treat results as `(platform, backend profile, runner profile, region, topology)` observations. Different backend profiles may be compared as *scaling studies* with their hardware and cost differences shown; never merge them into a single like-for-like platform comparison. A profile is feasible only if each stack under consideration can boot, seed the full fixture, pass correctness and operate without memory/disk pressure. A 4 GiB profile may be infeasible for some full stacks; mark those cases **unsupported/ineligible for that profile**, not zero-capacity failures, and do not quietly increase their VM size.

Configure the runner plan **independently** from the backend plan. It need not match the backend's RAM or CPU and may be held fixed across several backend profiles *if* diagnostic load proves headroom at every profile's peak. If it becomes the bottleneck, move to a larger declared runner profile and rerun affected observations; do not mix runner sizes within one comparison campaign. The goal is the smallest plan that consistently has ample measured headroom under the hardest expected workload, **not** an intrinsically optimal runner size. V3 already measures process CPU/RSS and event-loop delay and invalidates sustained CPU/event-loop overload; V4 must also capture runner host CPU/steal, memory/swap, NIC throughput/drops and connection limits so a runner that is IO-, memory- or network-limited cannot masquerade as a slow backend.

## Phases and exit gates

### Phase 0 — Freeze the experiment contract (no cloud resources)

- Specify primary claim: capacity under V3's existing 500/750/1000 ms class p95 limits, <1% errors, 95% achieved-user floor, workload mix, 5-second request timeout, 120-second warm-up and 300-second measured stages. State that same-region private RTT is part of the measurement. Keep V3's 1,000,000-record seed and three balanced repetitions per platform for a publishable comparison. Do not carry forward V3's fixed 600-second cooldown: V4 uses a fresh VM pair per independent observation and no arbitrary inter-platform delay.
- Use `us-west` when available at the same price as `us-lax`, otherwise use the cheaper of those two. Set the aggregate spend ceiling to USD $30 for the campaign, including both VM-hours and transfer. Use a fixed 8 GiB dedicated backend and 8 GiB dedicated pilot runner. Use platform-native HTTPS with a per-observation private CA; predeclare VPC design, storage type/size, instance image, CPU architecture, ordering, and allowed deviations. A future 4/16 GiB backend profile requires separate approval and budget; changing plan is not a change mid-run. Decide whether cross-platform comparison includes Neon given its materially different SQL-over-HTTP/app-owned-auth path; always label it separately.
- Estimate peak footprint and costs before provisioning. Enforce one active pair and a USD $30 aggregate campaign budget in the controller; stop before creating another pair if the remaining estimated budget is insufficient. G8 Dedicated has usage-based transfer and no monthly price cap, so use private VPC traffic, avoid retained volumes/snapshots, reserve budget for small result transfers, and document that external billing metering may lag. Do not implement an unattended loop that can create unlimited instances.
- **Gate:** reviewed methodology and budget; scope and credentials policy approved. V4's exact numerical results remain unknown.

### Phase 1 — Manual two-host feasibility pilot (one platform)

- Provision a single pair in the chosen region/network; confirm private IP connectivity, firewall rules, SSH, DNS/TLS/SDK behavior, packet RTT, clocks, storage, and host metrics. Install from a pinned clean checkout; prepare one platform with `bin/baas setup/start/smoke` **on the backend** and run a small V3-derived correctness/load diagnostic **on the runner**.
- Exercise setup/verification/reset/teardown on the backend, SDK authentication and all measured workflows from the runner, and sustained load sufficient to reveal runner event-loop, CPU, network or backend IO limits. Validate no public API exposure and no secrets in output. Confirm the backend can seed the full fixture without OOM or out-of-space failure; measure its setup time separately from timed load.
- Calibrate the runner separately: with a backend sized to remain responsive, increase load until the intended maximum stage or an obvious runner limit; observe CPU/event-loop, RSS versus available RAM, swap, host steal, NIC/drops and connection failures. If the backend saturates first, repeat with a less-constrained backend or a controlled diagnostic endpoint; do not claim the runner has unlimited headroom. Try a larger runner plan only if measured headroom is insufficient, then repeat calibration on the chosen plan. Keep these diagnostics out of publishable capacity results.
- Capture a minimal pilot report: both actual plan IDs/specs, image/versions/digests, network RTT/bandwidth, workload sanity, runner and backend resource utilization, estimated per-observation cost and duration. Pilot output is diagnostic, **not publishable V4 comparison evidence**.
- **Gate:** full fixture and correctness succeed on the 8 GiB backend plan; measured traffic goes through the intended private interface; calibrated runner has headroom at peak; backend telemetry is available. Otherwise revise the profile before implementing V4.

### Phase 2 — Separate the runtime roles and integrate the framework

- Scaffold `realworld-api-v4` with `bin/bench new` after the pilot, resolving all generated TODOs. Reuse V3 dataset, workloads, adapters, SLO/capacity logic and pinned dependencies rather than inventing a new benchmark. Keep cases and material deviations explicit. Any shared-code reuse must be snapshotted/checksummed with the selected definitions so a published run can be reconstructed from its recorded commit.
- Run platform lifecycle, administrative fixture work, verification and container telemetry **on the backend**; run the measured Node workload, SDKs, session creation and runner telemetry **on the runner**. The controller coordinates them, collects the two sets of outputs and publishes only through `bin/bench publish`. Preserve `bin/bench run` ownership of start/stop, setup, reset, verification and cleanup; avoid a second independent lifecycle that could bypass its manifests. Design the smallest remote invocation/transfer boundary necessary instead of forwarding a Docker socket to the runner or duplicating the entire framework.
- Inventory and adapt V3 assumptions before choosing the transport: `run.mjs` discovers `docker compose -p baas-<platform> ps` locally and samples Docker every second; `bin/bench` records local Docker/host environment and has a single-host lock; `case.sh` reads local `.runtime`; several SDKs/admin modules use localhost, local certs or Nhost virtual hostnames. Neon expects `https://localhost:4444/sql` and a local CA; Convex uses localhost in auth/issuer configuration. Every platform needs an explicit, verified HTTPS runner-facing endpoint and private-CA trust; keep backend administrative endpoints separate. Do not insert a shared TLS proxy or tunnel on the measured path. A platform-specific TLS terminator is acceptable only if it is part of that platform's native API gateway and is documented as the access path.
- Sample Compose-owned backend containers and backend host CPU/memory/disk/network on the backend; sample runner CPU/RSS/event-loop and host/network on the runner. Align timestamps and stage boundaries; note host clock skew. Missing/malformed samples, backend restart, packet loss/connection failures, runner saturation, or unaccounted resource contention invalidate attribution rather than reducing the reported capacity silently. Keep raw stage curves and failures locally; publish only compact, validated, sanitized evidence.
- Record **both** exact host plan IDs/profiles, region, network path, VM IDs as non-secret local diagnostics (omit public addresses and sensitive identifiers from published data), architecture/image/kernel, storage, Docker/Compose, SDK/runtime, Git commit, version digests, container configuration and relevant topology deviations. Extend the manifest/publication validator as needed so absent or mismatched remote provenance cannot produce a publishable V4 bundle. Ensure cross-host result transfer is atomic/checksummed; a successful process exit alone does not prove complete output.
- **Gate:** one end-to-end diagnostic `bin/bench run` and validation with fake remote commands and one live pilot case. Failed transfer/telemetry/cleanup remains visible; original errors survive cleanup errors.

### Phase 3 — Provisioning and cost-safe automation

- Add a small controller workflow using the Linode API (or an already available supported client): create exactly one tagged backend and one tagged runner in the approved region/plan/VPC, wait for readiness, configure hosts, verify private route, start the benchmark, retrieve evidence, and tear down only resources carrying this run's recorded IDs/tags. Store an instance inventory locally with restrictive permissions **before** proceeding to later steps; support resume/inspection after controller crashes or API timeouts rather than retrying ambiguous creation blindly.
- Never infer deletion targets from a broad tag query alone; require ownership/ID checks and explicit authorization for deletion. Always attempt cleanup, including after failure or interruption, but preserve the benchmark's original failure and report cleanup failures separately. Delete both instances and any billable attached volumes, snapshots, images or other run-owned resources after evidence is verified locally. Do not retain provider-side fixture snapshots in the baseline workflow. Have a manual recovery command/inventory and a TTL/spend alarm for stranded resources; do not assume traps run after power loss or `SIGKILL`. Avoid deleting persistent evidence until verified locally. Explicit confirmation is required before any billable provisioning and destructive teardown in a live account.
- Scope/redact token use, SSH bootstrap secrets and application credentials; avoid world-readable cloud-init/user-data and never publish connection strings, private keys, raw responses or fixture data. Smoke-test API client, provisioning and cleanup against mocks; live tests only with account-owner approval.
- After the controller has observed remote completion and attempted teardown, send a concise ntfy.sh notification when configured with an authenticated topic. Include only run ID, status, aggregate spend estimate and cleanup outcome. Keep topic/authentication settings outside the repository and logs. Notification failure must not mask run or teardown status; a controller crash still requires inventory-based recovery.
- **Gate:** create/inspect/recover/delete rehearsal for one pair, with failed-provision and failed-cleanup scenarios; zero untracked instances, and known maximum charge if interrupted.

### Phase 4 — Measurement validation and experimental control

- Check each case's complete remote workflow, including special hostnames, TLS, proxy/port requirements and protocol-specific behavior, before a comparison campaign. Verify fixture identity, tenant isolation and resets as V3 does. Document endpoint/topology differences in each case README.
- Establish runner headroom for worst-case stages for **each** backend profile; at high load, runner CPU/event-loop limits, RSS/swap pressure, host steal, NIC saturation/drops or failure to create requested sessions invalidate server-capacity claims. A backend that cannot provision the fixed million-record fixture on a small plan is ineligible for that profile, not a measured zero. Record private-path baseline RTT and jitter before/after every observation; reject or flag materially unstable network conditions using a threshold declared before the campaign. Compare repeated same-platform runs to quantify run-to-run variation, CPU steal/host contention, IO wait and thermal/host effects. Predeclare rules for valid/invalid observations; don't tune them after seeing winners.
- Test whole lifecycle, profile selection/provenance and publication checks with fake Linode API, fake SSH, fake Docker and fake hook commands; real integration diagnostics are kept distinct. Before implementation is called complete run the repository's required shell syntax, shell regression suites, `bin/bench validate all`, `git diff --check`, plus V4-specific Node tests.
- **Gate:** stable, correctly attributed repeated pilot observations, no secret leakage, and reproducible complete/failed manifests.

### Phase 5 — Balanced campaign and reporting

- For the 8 GiB backend profile, use a predeclared balanced/rotated order across included platforms and at least three valid independent observations per included platform. Each observation uses a fresh backend/runner pair; retain every attempt including invalid/interrupted runs and delete the pair after verified evidence transfer. No fixed cooldown is required. Record timestamps, provisioning details and telemetry to detect time-varying provider contention. Keep hardware, OS, networking, image and code revision identical within the campaign. Do not silently replace invalid attempts without recording them.
- Inspect complete capacity curves and resource traces, publish validated compact bundles through `bin/bench publish`, and report per-(platform, backend profile) distribution/variation, achieved load, class p95/error rates, throughput, calls/workflow, runner headroom, backend footprint, topology and cost context. When presenting 4/8/16 GiB scaling, show exact CPU/disk/network plan changes too; disclose excluded infeasible stacks and don't present a partial profile as an eight-platform comparison. Separate Neon access-path results; no unexplained composite ranking. State that same-region VPC load has lower latency than typical internet clients and that these are self-hosted configurations rather than hosted offerings.
- **Gate:** only claim a cross-platform comparison after the declared repetitions, clean definitions, valid telemetry/correctness and publication checks hold. A partial campaign is labeled diagnostic.

## Open decisions before live provisioning

1. How to provide the Linode token securely on the controller and an authenticated ntfy topic/token without committing either. The campaign budget is capped at USD $30; region preference is `us-west`, then `us-lax`, choosing the cheaper if prices differ.
2. Should a separate geographic/public-internet latency profile be studied later? If so, make it another declared profile, not a hidden change to this capacity experiment. Per-platform HTTPS endpoints, CA trust, Convex issuer, Nhost virtual hosts, and Neon proxy hostname remain implementation checks, not open topology choices.
